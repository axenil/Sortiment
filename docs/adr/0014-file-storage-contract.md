# 0014. File storage contract

- **Status:** Accepted
- **Date:** 2026-11-02

## Context

ADR 0008 defines `IFileStorage` for saving, reading and deleting file content, but not what an adapter guarantees. Two things are left open:

- **Failures.** Reading returns a `Result`, while saving and deleting only throw. Adapter authors cannot tell which failures are results and which are exceptions.
- **File facts.** An `AssetFile` records the size and SHA-256 checksum of its content, and asset families limit file sizes. Both are passed in by the caller, separately from the content that was saved. A caller that passes the wrong size gets past the family's size limit, and a wrong checksum breaks duplicate detection and integrity checks.

The first adapter, `Sortiment.FileStorage.FileSystem`, is built in step 3, so the contract should be settled first.

## Decision

- **Failures follow ADR 0005.** A file that does not exist is an expected outcome when reading, and is returned as the error `file_storage.not_found`. Saving and deleting have no expected failures: deleting a missing file succeeds. Every other failure, such as a full disk or an unreachable service, is an exception.
- **The adapter measures what it stores.** `SaveAsync` returns a `StoredFile` with the storage key, the size and the SHA-256 checksum of the bytes it actually wrote. Callers never supply these for new content.
- **`AssetFile` is built from a `StoredFile`.** The normal flow is to save the content, then describe it. Storage restores an `AssetFile` by building the `StoredFile` from its stored state.
- **Storage keys are generated by the adapter** and always satisfy `StorageKey`: a relative path of safe segments. Adapters only ever use keys that went through `StorageKey`, so a key can be appended to a storage root safely.

ADR 0008 is amended by this decision.

## Consequences

- An asset's recorded size and checksum always match the stored content, so asset family size limits cannot be bypassed by misreporting the size.
- Adapters compute the checksum while writing, in a single pass over the content.
- Asset family limits are still checked after the content is saved. Rejecting oversized uploads early, before they are written, is the job of the API, for example through request size limits.
